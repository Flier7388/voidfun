# Дорожная карта

*[Read in English](ROADMAP.md)*

Scope этого репозитория — **только desktop: Windows + Linux**, без
Android/iOS/macOS. Мобильный клиент планируется как **отдельный
репозиторий со своей дорожной картой**, а не как веха здесь.

## Правила

- Каждая веха содержит конкретные задачи с критериями приёмки
  (acceptance). Не начинать задачи следующей вехи, пока критерии
  текущей реально не выполнены. Исключение: **spikes** (ограниченные по
  времени эксперименты, например выбор архитектуры звонков) и работа над
  CI могут идти параллельно; результат spike не считается задачей вехи,
  пока не выполнен его acceptance.
- Каждая веха имеет тег направления: `base`, `security`, `chat`,
  `spaces`, `media`, `calls`, `quality`.
- Задача помечается `[x]` только когда критерий проверен на реальном
  homeserver (и, где указано, во втором клиенте, например Element), а не
  только покрыт unit-тестом.
- Всё, что обнаружено по ходу вехи и в неё не вписывается, идёт в
  **Backlog** внизу, а не в текущую веху.

## Почему такой порядок

1. **Шифрование раньше фич чата.** Большинство DM и приватных комнат
   по умолчанию зашифрованы end-to-end, поэтому ответы, реакции и медиа
   нельзя нормально проверить без работающего E2EE.
2. **Аккаунты и онбординг сразу после.** Регистрация, инвайты и join в
   комнаты нужны, прежде чем приложением сможет пользоваться кто-то,
   кроме автора.
3. **Чат → awareness → управление комнатами → медиа → звонки.** Каждый
   шаг опирается на предыдущий; звонки в конце, потому что это самая
   рискованная и наименее стандартизированная часть.
4. **CI для Flutter-приложения заводится рано**, а не в конце: это
   дёшево и ловит регрессии во всех следующих вехах.

## Текущее состояние — проверено 2026-11-09 (+ исправления до 2026-11-12)

**Backend** (`crates/matrix-client`, `matrix-sdk`/`matrix-sdk-ui` 0.19.1):
- Логин (username/password, голое имя сервера или полный URL) и
  восстановление сессии (хранится на стороне Flutter).
- Sync через `SyncService`.
- Joined-комнаты и top-level spaces: снимок + живые обновления. Дочерние
  комнаты space: только снимок.
- Timeline комнаты: снимок + живые обновления, фоновая подгрузка
  истории, отправка plain-text.
- Не сделано: верификация E2EE, регистрация, ответы, реакции,
  редактирование, поиск, read receipts, typing, медиа (есть только
  политика retention кэша), уведомления, голос/видео.

**UI** (Flutter + `flutter_rust_bridge`):
- Своя тёмная тема, настоящий 3-панельный layout (rail / список комнат /
  комната), экраны Home, Direct Messages и space, drawer участников,
  настройки (профиль + logout).
- Explore, Search, Inbox и большая часть Settings — явные заглушки
  «Not implemented yet».

**Платформы:** Linux собран и проверен запуском. Windows: Rust workspace
проверяется в CI, Flutter-сборка под Windows **ни разу не запускалась**
— не проверено.

**Тесты/CI:** 3 Rust-теста (mock homeserver) + 1 файл Flutter widget
test. CI гоняет `fmt`/`check`/`clippy`/`test`/`cargo-deny`/`cargo-audit`
на Ubuntu + Windows; Flutter-приложение пока не собирает.

**Тег сборки:** `0.1.0-alpha`.

  подтверждено живым клик-тестом.**
- Полная подгрузка истории через `paginate_backwards` (до 10 × 50

- Комнаты MSC3417 (call) были скрыты в списке комнат space; фильтр

## 0.2.0-alpha — шифрование и безопасность сессии `security`

**Цель:** зашифрованные комнаты работают как в любом нормальном клиенте,
а креды не лежат на диске открытым текстом.

- [ ] Отправка и приём в зашифрованной комнате.
  **Acceptance:** в комнате, созданной в Element с включённым
  шифрованием, сообщения с обеих сторон расшифровываются; нет «unable to
  decrypt» для сообщений, отправленных после логина.
- [ ] Показ состояния шифрования в UI.
  **Acceptance:** у зашифрованных комнат есть индикатор; нерасшифрованные
  события показывают понятную заглушку, а не пустую или сломанную строку.
- [ ] Верификация устройств (SAS emoji) — входящая и исходящая.
  **Acceptance:** верификация этой сессии против Element работает в обе
  стороны, обе стороны показывают её как verified.
- [ ] Cross-signing и secret storage: bootstrap на новом аккаунте,
  ввод recovery key на существующем.
  **Acceptance:** новый логин на аккаунте с зашифрованной историей +
  recovery key делает старые сообщения читаемыми (key backup
  восстановлен).
- [ ] Шифрованное локальное хранилище, секреты в OS keyring.
  **Acceptance:** нигде в каталоге данных приложения нет access token
  или passphrase хранилища открытым текстом (проверка grep) на Linux и
  Windows.
- [ ] Список сессий и удалённый выход.
  **Acceptance:** другие сессии аккаунта видны в списке; выход одной из
  них из этого приложения разлогинивает её в другом клиенте.

## Критерии релиза 1.0

1.0.0 не означает «реализован весь Matrix». Это значит, что основные
сценарии работают надёжно, безопасно и предсказуемо. Должно выполняться
всё перечисленное:

- Логин, регистрация, E2EE с верификацией устройств и восстановлением
  ключей, текстовый чат (ответ/реакция/правка/удаление), медиа и голосовые
  звонки 1:1 работают на **обеих** ОС, Linux и Windows, согласно
  письменному тест-логу из 0.9.0.
- Нет известных багов с падением, потерей данных или утечкой кредов в
  основных сценариях.
- Нет секретов (токены, ключи, тела сообщений) на диске или в логах
  открытым текстом.
- CI собирает и smoke-тестирует Flutter-приложение на обеих платформах;
  на чистой машине релизную сборку можно установить и запустить.
- Всё нереализованное в UI либо скрыто, либо явно помечено — никаких
  фейковых данных.
- Известные ограничения перечислены в пользовательской документации.
